The sync layer, rebuilt table by table

A ground-up rewrite of how SIMMER reads and writes data. TanStack DB is transport only, the server validates, every mutation names the command it means, and the only per-table definition is the schema. This page is where the work is tracked — it replaces HANDOFF.md.

Where it stands

The server half is nearly whole. The client is the long tail: 54 collection modules exist, the read seam is well along, and the write seam is four domains in.

packages/sync — done

One schema and one collection factory per table, generated from the database. The 55 sync descriptors and the factory that made them are deleted. mutateCollection carries single-row writes; commandTransaction carries the rest.

apps/server — nearly done

Shape routes derive from the scope map and the schema registry. Commands post per table to /commands/{table} and dispatch on an intents list, so no endpoint infers a command from which fields arrived.

apps/admin — done

The only app fully migrated. It has lib/collections/, hooks/queries/ and lib/collections/writes.ts; its sync/ folder and the nine /admin/* write functions are gone.

apps/web — mid-migration

Every surface still on webCollections is broken at runtime: rows arrive snake_case and the consumers read camelCase. Expected, and not worth chasing table by table — it resolves as each one migrates.

Multi-row is not "how many tables the server writes". It is whether the optimistic view is wrong without a second row written on the client. Deleting a Habitat writes four tables server-side and is still single-row here: the client removes one row, and the Comments it never loaded arrive over sync. Three shapes qualify — many rows the command names (a move, a merge), a parent and the children created with it, and a record plus the thing that produced it.

The four #162 names are single-row by intent and multi-row by accident. An add is one insert at a position between its neighbours, and position is double precision for exactly that — but the handlers insert at zero and renumber every sibling, so today they really do write N rows. Nothing is blocked on it.

The ten weather.* names have no handler anywhere — no route, no writer. They are vocabulary waiting for an endpoint, and their absence from the multi-row union is not a finding.

Next, in order

This one is a sequence: each step makes the next one smaller. The catalogs, the control products, the assets, the address book and every record surface are behind it.

  1. The record surfaces — done

    All three. Larval took the four performed control actions with it, because inspections/$id.tsx was the last thing reading applications, source_reductions, outreach_actions and biocontrol_actions through the old seam; adult took traps, collections and collection_species; public engagement took contacts and service_requests. What is left of this step is the list of traps they turned up, because every surface below still hits them.

    Four things larval turned up and adult confirmed, in the order they appear. A record's edit form wants the raw column, not the display projection — every one of these coalesces a null name into something readable, and a form field filled with that fallback saves it back as the name. The domain splits one form across more commands than the form has sections, and a save that names one it has no changed fields for is refused rather than ignored — so a form's current has to be built by the same round trip that builds its next values, or an untouched field compares unequal to itself. A control that mutates a draft is hiding several commands behind one callback: the sample detail's onPatch was four, and the collection page's three result switches were three. And a recording made from a stop is a multi-row command — SingleRowCommandType refuses it at compile time, it goes through commandTransaction, and because that sends the body it is handed rather than diffing one, the body-builder is where a missing stop id goes quiet behind a 201. All three of those builders are exported and tested directly.

    Adult added a fifth: a stored timestamptz arrives as a Date, and every place that turns one into a calendar day needs the agency's zone. Two surfaces were taking the UTC prefix instead, so a trap emptied at 10:30pm read as the next day in its own edit form while its detail page read the day the crew worked. Neither errored; they simply disagreed.

    Public engagement added two more, and both are about arguments rather than columns. A command can take something the table has no column for — a service request's contact and location are references, and contact_id holds where one landed — so the old endpoint reading the column back as the instruction meant an edit form that seeded the contact it already had sent a command with nothing to do, and the domain refuses one of those: the whole save failed over the half nobody touched. And a lifecycle command can take an id the old REST route was minting server-side — closing or reopening a request writes a comment, and its id is now the client's, so a retried close writes the same comment rather than a second one.

Conventions

Four decisions that are load-bearing, each with the reason attached — because each looks arbitrary without it.

snake_case all the way through the live queries. Table and column names stay as Postgres spells them, through useLiveQuery and into the predicates. The camelCase boundary is the query hook's output and packages/domain command arguments. Component props are camelCase and always were.

One module per table, no barrel. Each module calls createCollection at import, which a bundler cannot treat as side-effect-free. A barrel re-exporting 54 of them is the same indivisible node under another name — which is what put the whole collection graph in the boot chunk before, at 835 kB.

The Collection<Row, string | number> annotation on every const is load-bearing. A Collection<…> instantiated inside packages/sync arrives in apps/web as any, with no error anywhere. Writing the type out on this side instantiates it where it resolves. If one is ever removed, the check is that collection.id is refused where a number is wanted.

One hook per file, named for the hook. useHabitatSearch is use-habitat-search.ts. A file that is not a use- file is not a hook — shared.ts, and the per-domain view models.

How a hook is shaped

Read hooks/queries/shared.ts and hooks/mutations/shared.ts first — they carry the rules. The short version is below.

Surface hooks, not entity hooks. A hook returns the shape one surface needs, joined. An entity hook exists only where that entity is the page's subject — the Habitat detail page, the Habitat typeahead.

Transform in the query, with a compiled select. Not a .map() in the hook body, which re-runs every render and hands out new objects. A compiled select is part of the pipeline: it narrows what is materialized, and a row whose other columns moved produces no change downstream. A useMemo in a hook body is a sign the transform should have been a select — the one exception being an index over the rows, because a query returns rows and cannot return a lookup of them.

Exhaust the expression language before deciding it cannot say something: coalesce, caseWhen, concat, upper, length, the comparisons, the aggregates. fn.select takes arbitrary JavaScript and gives up both properties, and it receives the source namespaces rather than a prior projection, so a compiled select in front of it narrows nothing. Nothing in the folder needs it.

Join, do not waterfall. Reading ids from one query and feeding them to a second is a render round-trip and a second subset request. The join does it inside the pipeline and keeps up as rows arrive.

A write names the command it means, and only the commands it has fields for. Each server-side builder reads what it takes and ignores the rest, and the domain refuses a command with nothing to change — so a save that always names every intent breaks the moment a user touches one group of fields. Which intents a save means is a function of what actually changed, and working that out is the write hook's job.

Two commands against one row travel as one write. TanStack DB merges two updates to a key and keeps only the last metadata, so the first command's name would arrive carrying the second's fields and be dropped behind a 200. Rename-and-redraw is intent: ['…updateDetails', '…updateLocation'], not two calls.

orderBy is not honoured after groupBy

And it cannot read the projection either. A list needing both an order and a per-key count is two queries and a Map.

Strict SQL group-by, with no relaxation

Every non-aggregate column in the select must be in the groupBy — no functional-dependency exemption for a primary key. It throws at render; tsc sees nothing.

satisfies Row, never as Row

satisfies on an optimistic insert is what makes a wrong column name a compile error. The cast is exactly what let camelCase rows through in silence.

"Join requires an index" is not a failure

The warning is about the local snapshot pass, not the network, and appears with loading demonstrably correct. Every collection indexes id anyway.

A row of collections is an AdultCollection

Not a plural quirk — Collection is also what TanStack DB calls the thing that holds rows, so a module naming both cannot import them.

.limit() needs an .orderBy()

Without one it throws at render, with no diff to blame it on.

Traps

Every one of these cost real time, and every one of them fails silently — no error, no failing test, just a screen that is quietly wrong.

An empty transaction sends nothing

TanStack DB's commit returns early when mutations.length === 0: state completed, isPersisted resolved, mutationFn never called. A multi-row write whose apply touched no rows looks like a success and never leaves the browser.

Editing apps/server does not reload the command surface

A new route 404s and a changed payload reader silently ignores its key until the API dev server is restarted by hand. It presents as a client bug. Probe with a payload the new code must refuse and the old one ignores, using real foreign keys so an FK 500 cannot mask the answer.

subsetMethod: 'POST' is what makes joins work

A join asks for one IN over every join key it matched, and a couple of hundred uuids do not fit in a URL. On GET the request never lands and the query never becomes ready. Ten keys fit — so a small join works and a large one silently does not.

A left join yields undefined, not null

Every reference on an unmatched row is absent, so a fallback builds a label out of nothing. Guard on the driving row's own column. And prefer coalesce to caseWhen(isNull(…), …), which infers string | null because it cannot see the else branch is the column just tested.

awaitTxId needs a subscriber

A write into a collection nothing is querying does not settle slowly — it never settles. Reads and writes for a table must migrate together, and a create page warms its own stream by reading the row it is about to write.

A minimized Chrome window looks like a server bug

Background throttling stalls Electric's long-polls and surfaces as a CORS error on the boot-time shapes, with the app stuck on "Loading workspace". Foreground the window and re-test before diagnosing anything.

Verifying in the browser

Against the Railway staging database, through the local Caddy front at https://localhost:5175.

  • The worktree needs its own .env and apps/server/.env, copied from the main checkout — worktrees do not carry gitignored files, and without them the API dies with APP_ORIGIN must be set.
  • Sign-in is the user's job. Entering a password is off-limits. Ask, then continue.
  • Probing collections from the console gives false readings. Vite appends ?t= to HMR-invalidated modules, so importing a collection module builds a second instance that reads size: 0 while the page is visibly using the real one.
  • Patch window.fetch to read what a write actually sent. It is the difference between believing the client is correct and knowing it — and it is what settled the stale-API question.
  • Isolate before theorising. The subset bug looked like two queries interfering; removing one panel showed a single query loading zero rows, which pointed straight at the request.

Casualties

Deliberately removed, all approved.

  • getShapeServerUrl / VITE_SHAPE_SERVER_URL — the factory takes one serverUrl, and both deployed environments left it unset.
  • sync-modes.ts — each collection module states its own syncMode next to the collection it configures.
  • The nine /admin/* write routes — admin-foundations.ts is reads only, and a test asserts it registers no verb but GET.
  • The camelCase column mapper — which is why every unmigrated surface is broken rather than degraded. A subset predicate naming a camelCase column answers 400.
  • Unnamed Habitats label themselves with coordinates rather than a short id. Open cosmetic issue: the expression language has no round, so it renders full float precision beside formatCoordinates, which shows five places. The clean fix is rounding where the trigger writes them.
