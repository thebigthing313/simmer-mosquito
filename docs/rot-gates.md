# Rot gates

What each static gate in CI's `verify` job checks, why it exists, and the floors and probes under it. `CLAUDE.md` carries the short index; this is the reference. Each gate is one paragraph, and a new gate adds a paragraph here rather than editing a neighbour.

## fallow


CI's `verify` job runs three `fallow` checks. The first is a `check:*` gate and `pnpm check:all` runs it; the other two are not, and the `check:dead-code` paragraph below says why. All three are also runnable locally:

```sh
pnpm check:dead-code    # unused code, cycles, unresolved imports, gated at zero
pnpm fallow dead-code   # the same run, by hand, without the gate name
pnpm fallow dupes       # duplication, ratcheted at the threshold in .fallowrc.jsonc
pnpm fallow:health      # complexity, compared against .fallow-baseline/health.json
pnpm fallow:baseline    # re-save the complexity baseline after real complexity comes out
```

`dead-code` reads package source rather than build output, and that is what makes a local run and CI agree. A cross-package import resolves through the target's `exports`, which point at `dist/`, so the gate used to answer from whatever happened to be built in the checkout running it: unresolved imports in one that had never been built, a different answer fully built, a clean pass in CI, which runs it six steps before `pnpm build` (#334). Every export subpath that ships built output now carries a `fallow` condition naming the source behind it, and `.fallowrc.jsonc` asks for that condition. Nothing else reads it, so what the apps run is unchanged. **A new package owes the condition on every subpath that points at `dist/`, listed first**, and `pnpm check:build-graph` fails without it. First matters: fallow honours `types` as a built-in and takes the first key it matches, so a condition after `types` resolves to a `.d.ts` that an unbuilt checkout does not have, and is inert while looking like it works.

Duplication and complexity are gated **against where the workspace already is**, not against zero: the backlog is thousands of lines and hundreds of units, so an absolute gate would fail every branch on history. Read both as "did this branch make it worse". Lowering the duplication threshold or re-saving the complexity baseline is normal after a cleanup, but a re-saved baseline can also bury a regression, so read the diff. A `pnpm fallow:health` run ends with a verdict line from `scripts/fallow.mjs` naming the comparison's outcome and the run's exit code, because the `✗ n above threshold` line above it is fallow's own count of findings over its threshold and prints the same on a run that passes and one that fails (#941). A `pnpm fallow dupes` run ends on its own verdict too, naming the percentage measured, the threshold in `.fallowrc.jsonc` it was measured against and the exit code, because the `✗ n lines (p%) duplicated across m files` above it is fallow's own count and prints on a run that fails the threshold as well (#971).

A saved entry that matches no current finding is allowance nothing is using: the file it names was cleaned up, so a new finding there lands inside the old headroom and the gate stays quiet. `fallow` warns once a quarter of the saved entries match nothing, but it prints that ahead of 1500 lines of report and still exits 0, which is how the baseline sat five days with 358 of 658 entries matching nothing (#360). So `scripts/fallow.mjs` reprints the warning under the report and fails on it. A branch that trips it has cleaned real complexity out and should run `pnpm fallow:baseline`.

Under that quarter sits a second freshness gate, at five (#669). Below 25% `fallow` says nothing at all, and #605 was five entries of 166, three percent, which sat until a person read the file. So a run that compares against a baseline and saves none counts the stale entries itself: `scripts/fallow.mjs` saves a second baseline off the same tree into a temp file, and every saved entry the fresh one no longer names is stale. More than five fails, and the failure names them. The match is on identity, the file and the finding category, or the refactoring target key, and never on the count, because a count that happens to line up is exactly what a stale entry looks like. Read the failure as work already done rather than as a regression: complexity has come out and the baseline is holding headroom nothing uses, so the fix is `pnpm fallow:baseline` and reading the diff. That command saves rather than compares, which is #668's distinction, so it never runs this check and cannot fail on the condition it removes. The price is one more `fallow health` per gating run, about five seconds against the warm cache.

Both verdicts and the freshness count are re-derived rather than read off fallow, which prints no regression detail on a failing comparison, so #972 moved that half out of `scripts/fallow.mjs` into `scripts/lib/fallow-comparison.mjs` and put a guard under it. The move is the split the `packages/ui-web` contrast guard already makes: the wrapper spawns fallow on import, so nothing could import it and nothing tested it, and the suite now reaches the module through a hand-written `fallow-comparison.d.mts` beside it. **A function is in that module when it is total in its arguments and answers a question about the comparison**, which is what fallow was scoped over, what it matched on, what regressed, and what the verdict says; the child, the streams, the filesystem and the exit code stay in the wrapper, and so does `describeRun`, which is pure and is about the spawn. The guard is `unmodelledComparisonFlag`, and it refuses a gating run that passes `--baseline-mode` or `--tolerance` with a value the re-derivation is not written under, rather than printing a verdict beside an exit code that disagrees. `--baseline-mode identity` is the live case, measured on fallow 3.14.0: such a baseline carries a second key, `identity_finding_counts`, keyed by file, function name and category, which is what fallow compares and what `findingCounts` never reads, so an identity-only regression makes fallow exit 1 under a verdict reading `no regression`. `--tolerance` is guarded ahead of the fact instead, because measured against a baseline holding a two-count regression the run exits 1 at `0`, `2` and `100` alike, so on this version the flag does not reach the `--baseline` comparison and the two agree by accident. `PROBES` is the guard's own check and cannot be a floor: the refusal fires only on a flag nothing passes, and `pnpm check:all` runs no `fallow` gate, so a reader that has stopped reading flags prints the verdict a working one prints over the same counts, with every number unchanged. Six argument lists with known answers, three refused and three not, run ahead of the second fallow spawn.

## The static gates

The cheap static gates run in the same job and are not `fallow`. Each gate is one paragraph below, and a new gate adds a paragraph rather than editing a neighbour: this section of `CLAUDE.md` was a single 42,000-character line until #755, every gate-adding branch conflicted on it, and seven of the entries were sitting in the file twice by the time anyone read it end to end.

`pnpm check:all` runs all of them in one command, Biome first and then each gate in turn, and it is the pre-push command. `pnpm check` is still Biome alone and nothing folds a gate into it, because that would change what the one-word command costs. Nothing stops at the first failure: every gate runs and the summary at the end names the ones that failed, so a person about to fix things has the whole list. It takes about twenty seconds, of which Biome is three, `check:schemas` seven and `check:dead-code` under two warm, and the order is read off the job rather than written out again, so the cheap gates come first there and here alike. Membership is derived and there is no list of gate names in it, because a list is the register this issue was filed about: the issue title said fourteen, the triage brief corrected it to twenty-three, and the real number was twenty-four by the time either was read (#679). **A gate joins by being a `check:*` script in the root `package.json`, and by getting a step in CI's `verify` job.** Both halves, because `scripts/check-all.mjs` asserts the derived set against the `pnpm check:*` steps it parses out of that job, in both directions, and `pnpm check:all --list` is a step in the job that does that parse and runs no gate. So a gate added to one and not the other fails CI on the branch that wrote it, which is what keeps a local run and the job from disagreeing. `NOT_A_GATE` is the one hand-written register, three scripts with a reason each: `check:all` itself, `check:write`, which is `biome check --write` and a fixer, and `check:schema-drift`, which compares two live databases, needs `--observed` and `--expected` connection URLs and exits 2 without them, which is why CI does not run it either. An entry naming a script that no longer exists fails. The parse reads `run: pnpm check:*` lines and nothing else, which is the rule and also what kept a gate out of it: the dead-code step ran as `pnpm fallow dead-code` until #1152, so it was in the job and not in the command, and the `check:dead-code` paragraph below is what that cost. Two floors, #591's rule, because two parses are two ways to pass over nothing: a `package.json` this has stopped reading and a workflow this has stopped reading both leave the parity assertion true of two empty sets, under the summary line a clean run prints.

`pnpm check:dead-code` is `fallow dead-code` under the name that puts it in `pnpm check:all`, and nothing else about it changed: the script is `node scripts/fallow.mjs dead-code`, the wrapper is the one `pnpm fallow` runs, and `.fallowrc.jsonc` is untouched. It exists because the pre-push command ran no `fallow` gate at all. `check:all` reads its membership off the `pnpm check:*` steps in the `verify` job, the dead-code step was `run: pnpm fallow dead-code`, and that line matched nothing, so the gate was in CI and not in the command that is documented as the pre-push gate. #1149 is what that looked like: the branch deleted the callers of `parseOptionalDateFilter` in `apps/server/src/map-tiles.ts`, its PR body said every gate passed under `check:all`, and CI's Dead code step failed on the export. Nothing lied. The command had never run that gate. Measured when the issue was filed, a warm `pnpm fallow dead-code` was 3.7 seconds against `check:all`'s twenty, and on the branch that added the script it was 1.5, so the cost is a few seconds on a run that already takes twenty. Unused exports, unused files, unresolved imports and cycles are at zero with no allowance, which is what makes the gate fit: it fails on what a branch adds and never on a neighbour's history. The other two `fallow` runs stay out on purpose. `dupes` ratchets on the percentage in `.fallowrc.jsonc` and `health` compares against the saved baseline, so both are gated against where the workspace already is, and a branch can fail either for a cleanup it never made when the threshold or the baseline moved under it, and `health` spawns `fallow` twice, once to compare and once to save the fresh baseline the freshness count reads, so it is the slowest of the three by a distance. So they keep their `fallow` and `fallow:*` scripts, their own steps in the job, and no `check:*` name. What the gate cannot see is the shape #621 found: `.fallowrc.jsonc` names every package barrel as an entry point, so an export a barrel re-exports is live whether or not anything imports it, and an orphaned name behind `packages/domain/src/index.ts` passes here while the same name in an `apps/` module fails. `check:mapping-callers` is the gate for that, one package at a time.

`pnpm check:tileset-keys` holds one register of the twelve tileset names and the three lists that spell it. The register is `MapTilesetLayer` in `packages/db/src/domains/map-layers.ts`, whose header carries the mechanism. The lists are the keys of `MAP_SURFACES` in `packages/db/src/domains/map-surface-register.ts`, which is where the twelve map surfaces are declared; `createTileSetRegistry` in `apps/server/src/map-tiles.ts`, which is what `/map/tiles/:tileset` answers on; and `TILE_LAYER_BINDINGS` in `apps/web/src/components/map/tile-layers.ts`, the table a `MapCanvas` layer names, whose `*_SOURCE_ID` is the string that goes in the path. `pnpm check:mapping-callers` is the gate `fallow dead-code` cannot be, and the two do not disagree. `.fallowrc.jsonc` names `packages/*/src/index.ts` as an entry point, so a package barrel is a graph root, and a barrel re-exports every module beside it. Every one of those modules is therefore reachable and every name in it live, which is how `features.ts`, `overlays.ts`, `tiles.ts` and `viewport.ts` sat in `packages/mapping` contributing 33 of the barrel's 115 names with not one of the 33 imported anywhere, two of them carrying suites, and one publishing a tileset union naming four tilesets that do not exist (#621). Moving the `entry` list is not the fix, because the barrel is a real root for every other package. So this asks the other question: not "is it reachable" but "does anything outside the package ask for it". The entries come from the `exports` map read through the `fallow` condition, a barrel is live because it is the published surface, a module the barrel re-exports is live only when one of the names it contributes is imported outside the package, and the walk then follows relative imports, which is what keeps `kmz.ts` alive behind `geometry-import.ts`. **The barrel's own imports do not propagate**, and that one line is the whole departure: with it in, this agrees with `fallow` and reports nothing, which is what the first run did. A suite is not a caller and `src/tests` is never walked, because a module with no caller collecting a suite is the shape #621 found twice. An `export *` in an entry module fails rather than being skipped, since a star names no names and every module behind it would count as live. **It judges value names as well as modules, since #1553.** One asked-for name keeps its module live and every other name the module publishes rode along with it, which is how five helpers sat in the barrel with no caller outside, and the first run of the name rule found three more, `normalizeGeomType`, `ringAreaMeters` and `sketchCrossings`. So every name in a value re-export clause, `export { a } from`, must be named by an import outside the package, read off the scan the module rule uses. Types are not read, `export type` clauses and inline `type` entries alike, because a type describes a value a caller receives and can be used through inference without being named.
