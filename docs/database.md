# Database

SQL migrations are the **source of truth**; dbmate applies them, Kysely is the server query builder.

```sh
pnpm db:migrate     # dbmate up   (packages/db/migrations -> packages/db/schema.sql)
pnpm db:rollback
pnpm db:status
pnpm db:vacuum-catalogs   # vacuum full over the system catalogs; the paragraph below says when
```

`packages/db/schema.sql` is checked in and is the dump `db:migrate` writes, which makes it the input to `pnpm generate:table-types`. That writes `packages/db/src/tables.ts`, so **a migration is three commands: write it, `pnpm db:migrate`, `pnpm generate:table-types`**. Miss the second and `check:table-types` says the dump does not name your migration; miss the third and it says the file is not what the dump produces. dbmate writes the dump by running `pg_dump` from your PATH and never reaches into a container on its own; the paragraph below says which version the wrapper accepts and when it uses the container's instead. dbmate also ignores a failed dump, so on a machine with no `pg_dump` the bare command applied the migration, left `schema.sql` alone and exited 0. `pnpm db:migrate` is `scripts/db-migrate.mjs` rather than dbmate for that reason. It refuses before applying anything when it has no `pg_dump` it can use, and it fails after dbmate returns when a run applied a migration and did not rewrite `schema.sql`, or rewrote it without naming every applied version, which is what a `pg_dump` older than the server looks like. Arguments pass through to dbmate, and `--no-dump-schema` turns both checks off. `pnpm db:rollback` runs through the same script and takes the same two checks, since dbmate drops a failed dump there too and the stale `schema.sql` then names a version the database no longer has, which `check:table-types` cannot see while the migration's file is still on disk (#1304). It refuses before rolling back on the same terms, and fails when a run printed a `Rolling back:` line and did not rewrite `schema.sql`, or rewrote it still naming that version. ADR 0004 is the rest.

**The dump is written with `pg_dump` 17.5**, the version the compose container, CI's service container and staging all run, and any 17.x up to 17.5 writes the same bytes (#1305). Two things in the file pin it. `SET transaction_timeout = 0;` is a line only `pg_dump` 17 writes, and 16 cannot be used at all, since it aborts on a server newer than itself. And the file has no `\restrict` line: from 17.6 on, dbmate 2.33 passes `--restrict-key=dbmate`, so the dump gains `\restrict dbmate` at the top, `\unrestrict dbmate` at the bottom, and a `-- Dumped from` and a `-- Dumped by` comment naming the server's and the client's versions, which would then change with every patch release of either. Measured through dbmate's own flags on a scratch database with every migration applied, 17.0 and 17.5 wrote the checked-in file, and 17.6, 17.11 and 18.6 each added those 8 lines. So a newer client is not safe here, and neither is a Windows installer that ships only the current 17.x. That is why the image is pinned by digest rather than by the floating `postgis/postgis:17-3.5` tag, in `docker-compose.yml`, CI's `Database integration tests` job and `schema-drift.yml` alike, all three naming one digest whose `PG_VERSION` is 17.5 (#1321): a rebuild of the tag on 17.6 would otherwise refuse the container's client on every branch at once. Moving the digest to one with a newer client changes the dump, so it means regenerating `schema.sql` through that client and moving the version window in `scripts/lib/schema-dump.mjs` in the same branch. The dump also covers the `public` schema alone, which dbmate asks `pg_dump` for when the URL it reads carries `search_path=public`. Without it the dump adds a `CREATE EXTENSION` and its comment for each of the four extensions and drops `CREATE SCHEMA public`, 54 lines on a fresh database, and against the compose database it would also take in the `tiger` and `topology` schemas the PostGIS image installs there. `.env`'s `DATABASE_URL` does not carry the parameter because the dev server reads that variable too, so the wrapper adds it: it resolves the URL dbmate would read, from `--url`, the variable `--env` names, the process or each env file, adds `search_path=public` when the URL has no `search_path`, and hands dbmate the result in `SIMMER_DBMATE_URL` through `--env`. Nothing needs passing by hand, and the URL never goes through `cmd.exe`, which splits an argument at `&` when `pnpm.cmd` runs the script.

**The wrapper reads `pg_dump --version` before dbmate runs and takes only 17.0 to 17.5** (#1315). With no `pg_dump` on the PATH, or one outside that range, it falls back to the compose container's client, which is 17.5: it finds the one container publishing `55432`, the way `pnpm db:vacuum-catalogs` does, writes a `pg_dump.cmd` (a shell script elsewhere) into a temporary directory first on dbmate's PATH, and says so on stdout, naming the container and why the local client was passed over. The shim is `scripts/container-pg-dump.mjs`: it runs `docker exec <container> pg_dump` with dbmate's arguments, `--version` included, and rewrites the URL's `127.0.0.1:55432` to the container's own `127.0.0.1:5432`. Through it, `pnpm db:migrate` and `pnpm db:rollback` wrote the checked-in file byte for byte against a scratch database with no `pg_dump` installed. The fallback needs the URL to reach the compose Postgres on `127.0.0.1:55432`, and on Windows it needs that URL to carry at most one query parameter besides `search_path`, because the shim is a `.cmd` and dbmate hands it the URL less `search_path`, which `cmd.exe` would split at the `&`. Otherwise the run is refused before dbmate starts, and the refusal names the version found, its path, and why the container could not stand in. `node scripts/db-migrate.mjs dump` rewrites the dump from the database with the same client choice and URL, which is what the stale-dump message points at. A dump of the compose database can still differ where the prod clone left objects in `public` that no migration made, and that is a question about the database rather than about `pg_dump`. **CI compares the dump's bytes in one place**, the last step of the `Database integration tests` job (#1316). Every other workflow runs dbmate with `--no-dump-schema`, and `check:table-types` reads only the versions the dump names and the types it produces, so until then a hand edit, a dump from another `pg_dump` or a migration committed without its dump passed every gate, and #1305 found a blank line that had been missing since the file's first commit. The step creates a database of its own in the job's service container, gives it the four extensions, copies the checked-in file aside, runs `node scripts/db-migrate.mjs up` against it, and fails with a `diff -u` when the file it wrote is not the one checked in. It is the wrapper a contributor runs, so the two cannot disagree about the URL or the client: the runner's own `pg_dump` is outside 17.0 to 17.5, the wrapper falls back to the service container's 17.5, and that is why the job publishes the container on `55432` as the compose file does. It is a step and not a `check:*` gate because it needs a database, which is `check:schema-drift`'s reason for sitting in `NOT_A_GATE`, and the job already starts one. A failure there is fixed by `pnpm db:migrate` or `node scripts/db-migrate.mjs dump` and committing what it writes.

Fast tests are pure (no DB). Postgres-backed integration tests (`*.integration.test.ts`) are **opt-in** and require an explicit test DB. They live in `packages/db/src/tests/integration` and `apps/server/src/tests/integration`, the latter for the ownership and lifecycle reads that decide whether a write happens, which take a plain `Transaction` and no server context. `apps/server` imports the harness from `@simmer-mosquito/db/test-support`, so `packages/db` must be built first.

```sh
# PowerShell. Start the local Postgres, then point the suites at it:
docker compose up -d postgres
$env:TEST_DATABASE_URL='postgres://postgres:postgres@127.0.0.1:55432/simmer_mosquito'
pnpm --filter @simmer-mosquito/db test
pnpm --filter @simmer-mosquito/server test
```

**On Windows the host is `127.0.0.1`, not `localhost`, and `withTestDb` refuses the name, and so does `readServerEnv`, for `DATABASE_URL` and `ELECTRIC_URL`, because the dev server opens the same burst on a dashboard read or a page of shape long-polls and met the same `ECONNRESET` out of `pg-pool` and out of `fetch` in `proxyElectricShape`.** Two things contend under a full `pnpm test`, and #926 was filed as one. The first is not the container: it is Docker Desktop's port proxy, and only its IPv6 half. Node resolves `localhost` to `::1` first, Docker publishes the port on `[::]` as well as `0.0.0.0`, and under the burst of connects a run opens, eleven workers each starting a pool at once, the `::1` listener accepts the TCP connection and never completes the half to the container, then resets it at exactly thirty seconds. That one hung connect is both faces the issue names: a test that times out at 45s because a query inside it never got a connection, and `read ECONNRESET` on a file that passes alone, which three agents in one week read as load. It was measured with an independent client opening five connections a second beside `packages/db` at eleven workers on a fresh container: over `localhost`, 60 of 450 connects hung and were reset at 30,000ms while the other 390 took 12ms; over `127.0.0.1`, 450 of 450 connected and the suite passed 311 of 311. No worker count reaches it, since four workers gave 25 failures against eight at eleven, and Postgres logged nothing for any of it, because the hung connect never got there. CI is untouched: its service container is reached over `localhost` on Linux, where there is no such proxy, and the refusal reads `process.platform`. The second is the container, and only once the first is out of the way: Nx runs three projects at a time, so `apps/web`, `packages/db` and `apps/server` overlap at eleven forks each on twelve cores, the Docker VM running Postgres is starved with them, a `docker exec psql` that took two seconds took 28, and every test on every worker timed out twice over while 60 throwaway schemas sat live at once, because a timed-out test leaves its schema build running. `vitest.shared.ts` holds the two database-backed projects at four workers, which is the number its floor already argued for, and the full run went from 261s with 42 timeouts to 213s clean; the comment on `DATABASE_TEST_FILE_WORKERS` carries the rest, including why serialising the two projects in Nx was measured and not taken. So a fresh `ECONNRESET` on Windows now means one thing, the URL, and a spray of 45s timeouts across both projects means the container is starved, and the first question is what else is running. A third, slower thing is real and is neither: the compose container carries months of `simmer_test_*` builds in its system catalogs, 181 MB of `pg_depend` and 75 MB of `pg_attribute` for zero live rows, and autovacuum never shrinks a catalog, so the same suite that takes 4.6s on a fresh container took 27s there when #926 was filed. `vacuum full` on those catalogs is the cure, and `pnpm db:vacuum-catalogs` runs it; the paragraph below is when.

Never point `TEST_DATABASE_URL` at the Railway staging `DATABASE_URL`. The migration set applies as one transaction creating 326 relations, which overruns the logical decoder's 1 GB reorder buffer and kills the walsender for good. That is how staging's Electric sync died (#166, #236). `withTestDb` reads `pg_replication_slots` and refuses to run when it finds a row, with no flag or variable past it.

If you have ever started the local Electric, that same container carries its `electric_slot_default` and the suites refuse it until you drop the slot with `select pg_drop_replication_slot('electric_slot_default');`. A local Electric recreates it on next boot, so it costs one re-snapshot. The refusal message says this too, and says it only for the container in front of you.

The compose service is also the only local Postgres these suites run on out of the box. Several files build their schemas at once, so the lock table holds every object of all of them and the stock `max_locks_per_transaction=64` fails twelve files at once with `out of shared memory` (SQLSTATE 53200). `docker-compose.yml` raises it to 1024 and creates `postgis`, `pgcrypto`, `pg_trgm` and `btree_gin` in `public` first, so the migrations' `create extension if not exists` is the no-op it expects; a hand-started container needs both.

Each test builds a throwaway `simmer_test_*` schema, applies every migration into it as a single query, and drops it afterwards, so `public` is never touched. That is about a second per test against the container, and `describeDbIntegration` sets its own 45s timeout; do not run these suites under vitest's default. Without `TEST_DATABASE_URL` they **skip silently**, so a green `pnpm test` does not mean they ran.

**A timed-out test no longer keeps its schema.** vitest aborts a test's context signal when the test times out or the run is cancelled, `describeDbIntegration` records that signal in a `beforeEach`, and `withTestDb` reads it: on abort it cancels every backend it opened through `pg_cancel_backend` from a second connection, drops the schema whether or not the build had finished, and rejects with `TestDbAbortedError` naming the abort rather than the `57014 query_canceled` the interrupted query threw. Before #1038 nothing told the harness, so the schema build or the test's own query ran to completion on its backend and only then did the `finally` drop the schema; measured with a `pg_sleep(60)` under a 3s timeout, the schema and its active backend outlived the test by the whole sleep, and the schema stayed for good when the worker exited before the sleep ended, against under a second after. The wrapper's `afterEach` and `afterAll` wait for that cleanup before the next test starts and before the file ends, because a timeout on a file's last test otherwise ends the file with the drop still on the wire, and vitest recycles the worker under it. Every pool the harness opens carries the schema name as `application_name`, so `pg_stat_activity` says which test a backend belongs to. A pool that will not drain or a drop that fails after an abort is a warning on stderr naming the schema, bounded at ten seconds, and the once-per-run sweep collects it: the cutoff is thirty minutes, because no test outlives its file and the watchdog kills a file at eight. `TestDbOptions.signal` takes a signal of the caller's own; the 282 existing call sites pass nothing and get the test's.

**A db suite several times slower than its neighbours on an old container is the catalogs, and `pnpm db:vacuum-catalogs` is the fix.** Every throwaway schema writes a few thousand rows into `pg_depend`, `pg_attribute`, `pg_class` and their neighbours and deletes them again, and autovacuum reuses the space inside a catalog but never shrinks the file, so months of runs leave `pg_depend` at 149 MB for zero live rows, measured on 2026-09-17 against #926's 181 MB, and every schema build walks all of it. The script runs `vacuum full` over fifteen catalogs through `docker exec` on the container publishing `55432`, so it needs no local `psql` and reaches a hand-started container that is in no compose project, and prints each catalog's size before and after. **It refuses to run while any other client backend is on the database**, because `vacuum full` takes an access exclusive lock on each catalog for the whole rewrite and a suite building a schema would queue on every statement; the refusal lists each connection and says which are the local Electric's pool and which are processes on this machine, so `docker compose stop electric` and stopping the dev API server are the usual two steps before it, and `docker compose start electric` the one after. CI never needs it, since the service container is fresh every job (#1104). It is a fixer rather than a gate, so it is not a `check:*` script and `pnpm check:all` neither runs it nor has to excuse it.

CI runs them the same way. The `Database integration tests` job starts a `postgis/postgis:17-3.5` service container, the version staging runs, and points `TEST_DATABASE_URL` at loopback, so nothing CI does reaches the database your dev server is talking to.

**Local dev backends:** everything runs on your machine. `apps/server` and the frontends run locally, and Postgres and Electric come from `docker-compose.yml` (`docker compose up -d postgres electric`, with `.env` and `apps/server/.env` on the `.env.example` values and `ELECTRIC_SECRET` unset). The compose file pins `name: simmer-mosquito`, because compose otherwise derives the project from the directory holding the file, and a compose command from an agent worktree under `.claude/worktrees/` then addressed a project that did not exist and answered `service "postgres" is not running` while the container was up (#1122). **Nothing local points at Railway.** Staging is a sandbox organization staff sign into, so a local dev server writing to it corrupts their test; there is no documented escape hatch back to it. Local data comes from `scripts/clone-prod-db.ps1`, which clones prod into the compose Postgres, prunes to the last 3 years of dated records, and relinks the cloned prod WorkOS ids to the WorkOS **staging** ids local dev signs in against. See `docs/deployment.md`, "Local development" and "Cloning production data". Deploys are gated on `pnpm test` passing (`verify` job), so keep tests green or nothing deploys. Pushing `main` is a production release, and `railway-deploy.yml` is the only way into either Railway environment; nothing on Railway's side watches a branch.

**Staging is a user-facing sandbox, not a scratch environment.** It holds a full-history clone of production and authenticates against WorkOS **production**, so its sign-ins are real identities. `WORKOS_IDENTITY_WRITES_DISABLED=true` is set on the staging server, which refuses every WorkOS identity write with 403 `workos_identity_writes_disabled`: inviting, changing a role, removing access, resetting a password, signing up and creating an Organization all refuse there, while signing in and switching Organization work. Read ADR 0017 before touching anything that calls WorkOS. The five role-ladder test accounts are WorkOS **staging** logins and do not exist there; role testing runs locally.
